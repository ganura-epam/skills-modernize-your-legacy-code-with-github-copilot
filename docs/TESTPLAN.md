# COBOL Account Management System Test Plan

This document provides a stakeholder-facing validation checklist for the current COBOL business logic and implementation. It is intended to support future migration to a Node.js application while preserving the legacy behavior and business intent.

| Test Case ID | Test Case Description | Pre-conditions | Test Steps | Expected Result | Actual Result | Status (Pass/Fail) | Comments |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TC-01 | Program starts and displays the account management menu. | The COBOL program is launched from the command line; no prior user state exists. | 1. Start the program. 2. Observe the initial screen output. | The application displays a menu with four options: "1. View Balance", "2. Credit Account", "3. Debit Account", and "4. Exit". The user is prompted to enter a choice between 1 and 4. |  | TBD | Confirms that the application presents the expected user entry flow and default user experience. |
| TC-02 | User chooses a valid menu option to view the current balance. | Program is running; initial stored balance is 1000.00. | 1. Select option 1 from the menu. 2. Observe the displayed value. | The system reads the stored balance and displays: "Current balance: 1000.00". No changes are made to the balance. |  | TBD | This validates the initial balance and the READ branch of the data program. |
| TC-03 | User enters an invalid menu choice. | Program is running; user is at the main menu prompt. | 1. Enter a number outside the valid range such as 0, 5, or a non-numeric value. 2. Observe the outcome. | The system displays: "Invalid choice, please select 1-4." and returns to the menu prompt without altering the balance. |  | TBD | This covers input validation and protects against unsupported menu selections. |
| TC-04 | User credits the account with a valid amount. | Program is running; existing balance is known; there are no validation constraints on the amount beyond numeric input. | 1. Select option 2. 2. Enter a credit amount such as 250.00. 3. Observe the updated balance. | The program prompts for the credit amount, reads the current balance, adds the entered amount to it, stores the new balance, and displays: "Amount credited. New balance: <updated balance>". The new balance should be 1250.00 if the starting balance was 1000.00. |  | TBD | This validates the core credit transaction and the WRITE path that persists the updated balance. |
| TC-05 | User debits the account with sufficient funds. | Program is running; current balance is at least the debit amount. Example: balance is 1000.00. | 1. Select option 3. 2. Enter a debit amount such as 300.00. 3. Observe the result. | The system prompts for the debit amount, reads the current balance, subtracts the amount if funds are sufficient, stores the updated balance, and displays: "Amount debited. New balance: <updated balance>". The new balance should be 700.00 if the starting balance was 1000.00. |  | TBD | This validates the successful debit transaction and confirms the subtraction logic. |
| TC-06 | User attempts to debit the account with insufficient funds. | Program is running; current balance is less than the entered debit amount. Example: balance is 100.00 and user attempts to debit 200.00. | 1. Select option 3. 2. Enter an amount greater than the current balance. 3. Observe the program result. | The system displays: "Insufficient funds for this debit." The account balance remains unchanged and is not written to storage. |  | TBD | This ensures funds protection and verifies the business rule for preventing overdrafts. |
| TC-07 | Balance persists across transactions. | Program is running; a prior transaction has updated the stored balance. Example: balance is 1250.00 after a credit. | 1. Credit the account by 250.00. 2. View the balance. 3. Debit the account by 100.00. 4. View the balance again. | The balance reflects the cumulative result of the earlier transaction. Example: after crediting 250.00, balance is 1250.00; after debiting 100.00, balance is 1150.00; viewing the balance returns the latest stored value. |  | TBD | This validates the persistence model and the use of the shared storage record for all account operations. |
| TC-08 | User exits the application from the main menu. | Program is running and the user is at the menu prompt. | 1. Select option 4. 2. Observe the end-of-program behavior. | The application sets the stop flag to "NO", exits the loop, prints: "Exiting the program. Goodbye!", and terminates gracefully. |  | TBD | This confirms the lifecycle end state and user-initiated termination behavior. |
| TC-09 | System reads and writes the stored balance using the shared data program. | Program is running; the data storage value exists and represents the current account balance. | 1. Invoke any balance-changing or balance-viewing action. 2. Review the state before and after the action. | The read operation returns the stored balance exactly as persisted in memory, and the write operation updates that storage value for subsequent reads. |  | TBD | This covers the implementation-level data contract between the operations program and the data program. |
| TC-10 | Program supports repeated transaction cycles until user exits. | Program is running; user can continue making transactions after each result. | 1. Select a valid transaction such as credit or debit. 2. Return to the main menu. 3. Repeat at least two additional action selections. 4. Eventually choose exit. | The loop continues indefinitely until the user chooses option 4. The menu is redisplayed after each transaction, and the program only terminates when the exit option is selected. |  | TBD | This validates the control-flow loop that drives the entire interactive application. |
